Guide · terrain / heightmaps

Large Heightmaps

A terrain can take its ground from a real-world elevation model (a DEM) instead of procedural noise: export it as a raw heightmap, set its grid in the asset's import settings, and pick it as the terrain's base. This page is the import, the binding from the inspector and from code, what re-reads when, the sizes at which streaming takes over, and what a large terrain costs.

The short version

Four steps.

  1. Export the DEM as .r32 (32-bit float heights in meters, row by row, the first row on the south edge) and drop it into the project. It imports as a Terrain Heightmap asset.
  2. Select the asset and set its Samples X to the samples per row it was exported with; Samples Z follows from the file. A square file needs nothing.
  3. Select the terrain, set Base Source to Heightmap and pick the asset.
  4. Set Size X and Size Z to the extent in meters, Height Scale to 1, and Samples Per Meter to the density you want the terrain to have.

Importing a DEM

Three formats are read as a terrain's base:

FileSamplesHeight in the world
.r3232-bit float, little-endian, row-majorsample × Height Scale. With Height Scale 1 a sample is meters.
.r1616-bit unsigned, little-endian, row-majorsample / 65535 × Height Scale
16-bit PNGimported as a Texture assetvalue / 65535 × Height Scale

A raw file is the samples and nothing else. The first row is the terrain's edge at the smallest Z; each row runs along +X. Its grid is the asset's Import Settings, shown in its inspector with the file's format and sample count:

  • Samples X: samples per row (along X). Samples Z: rows (along Z).
  • Set one and leave the other at 0: the other is the file's sample count divided by it. A value that does not divide the count is refused, with the nearest values that do.
  • Both left at 0, the grid is assumed square. A non-square file whose sample count is not a square number is refused; the notice says to set Samples X.
  • Both set, they must account for every sample of the file, or the heightmap is refused with the numbers that disagree.
  • Each edit can be undone.

A non-square file with a square sample count reads as stripes until its grid is set.

16384 × 4096 is 8192² samples, so with no grid set it reads as an 8192 × 8192 grid: each row is half a source row and neighboring rows alternate between the two halves. On a canyon DEM the height step between neighboring rows jumps from about 1 m to about 200 m, and the terrain looks like noise. The asset inspector says which grid the file reads as; set the real one.

The sidecar files some exporters write (.hdr, .json, world files) are not read. The terrain does not read the DEM's own spacing either: the meters per DEM sample is the terrain's size divided by the samples: Size X / (Samples X − 1) along X. The Terrain inspector's Base section says when the heightmap's shape does not match Size X : Size Z (including Samples X and Samples Z typed the wrong way round), and when Samples Per Meter is finer than the heightmap, with a Match Heightmap action that sets it to the heightmap's density.

Binding it as the base

From the inspector

The Terrain inspector's Base section (planar terrains) holds Base Source (Procedural Noise, Heightmap, Flat) and, for Heightmap, the Heightmap asset field. When the heightmap gives no heights, the section says why and offers Select Heightmap, which selects the asset so its Samples X and Samples Z can be set.

From code

auto& terrain = *world.GetComponent<Components::Terrain>(entity);
terrain.BaseSource = Components::TerrainBaseSource::HeightmapAsset;
terrain.TerrainAssetGuid.Set(heightmapGuid);
terrain.SizeX = 8192.0f;
terrain.SizeZ = 2048.0f;
terrain.HeightScale = 1.0f;
terrain.SamplesPerMeter = 2.0f;

Nothing else is needed: the terrain notices the change on the next frame.

From the debug port

set_component Terrain {"baseSource": 1, "terrainAsset": "<heightmap guid>"}

The GUID is the 8-4-4-4-12 hex form; "" or 0 clears it.

baseSource is the number (0 noise, 1 heightmap, 2 flat). get_entity_components reports BaseSource and TerrainAsset.

What re-reads, and when

ChangeWhat happens
Base Source or the heightmap assetThe next frame rebuilds the terrain's ground from the new base: a streamed terrain rebuilds its tile set; a small one refills its heights and re-applies its modifiers.
The file on disk (re-export)Re-read the next frame; the same rebuild.
The heightmap's Samples X or Samples ZRe-read through the same path as a re-export.
Size, Samples Per MeterRebuilt once the value stops changing (a drag rebuilds once, at the end).

Modifiers (sculpt, flatten, paint, surface rules) apply on top of the base and are re-applied after it changes; they do not replace it.

Sizes, streaming and the atlas

The terrain's density is Samples Per Meter, not the DEM's: the DEM is resampled onto the terrain's own grid. What that grid costs follows from the samples along the longer side:

Samples along the longer sideHow it is held
up to 1025One heightmap, always resident.
1026 to 8193Tiles of 1025 samples, all resident, drawn from one whole-terrain texture.
above 8193Tiles stream into a resident window around the camera at full detail; everything outside it is drawn from one coarse field spanning the whole terrain.

The Terrain inspector states the plan for the current values (tiles, resident window, coarse-field spacing, predicted memory) before you commit them.

What a large terrain costs

  • GPU memory follows the terrain's samples, not the DEM's: the height, splat and normal maps hold every resident sample, so doubling Samples Per Meter quadruples them. The inspector's sizing notice states the prediction for the current values. A kilometers-wide field at 0.5 m already fills the resident window's budget.
  • CPU memory: the decoded DEM stays in memory while a terrain uses it, 4 bytes per sample for .r32.
  • Frame time is highest at flight altitude, where the terrain refines across the whole view and a dense near field keeps its triangle pool close to full; at eye level and from far away it is low.
  • Finer than 0.5 m over kilometers: split the data into a smaller high-detail terrain over the area that needs it.

Cooked terrain pages

A raw heightmap (.r16 or .r32) is also cooked into a page store: the heightmap as a pyramid of small pages, each level half the resolution of the one below, which the terrain will stream a page at a time instead of decoding the whole file.

  • Cooked stores live in the project's .Cache/TerrainPages folder, one per heightmap, named for the asset and its content. Two terrains on the same heightmap share one store. After an edit of the heightmap, or of its Samples X and Samples Z, the next export cooks it again; an edit that keeps the height range rewrites only the pages that changed.
  • The folder is derived data: deleting it is safe, and it is rebuilt on the next cook. Keep it out of version control, like the rest of .Cache.
  • Exporting the game packs each shipped heightmap's store into one file, Assets/Cooked/Terrain/<asset id>.geterrain, cooking it first if it changed. A heightmap whose grid cannot be resolved is reported in the export's warnings, with the fix.
  • A cook reads the heightmap a band of rows at a time, so its memory does not grow with the file. Measured on a 60 × 15 km heightmap at 0.25 m (57.6 GB of .r32): about 50 s to read the file once and 2.5 min to cook a 79 GB store, on a fast NVMe drive.
  • 16-bit PNG heightmaps are not cooked into pages; they keep the limit stated below.

What streams at runtime

  • A streamed terrain (tiles, above 1025 samples along the longer side) on a raw heightmap draws its height from its pages: the pages under and near the camera at full detail, coarser levels further out, a page loaded when it comes into view and released 30 frames after it leaves it. The splat and normal maps still stream as tiles.
  • Height modifiers (stamps, flattens, corridors, zones, brush strokes) reach the pages: the terrain shows them from its first frame, and an edit rewrites only the pages it touched. The modifiers are baked on the terrain's tile grid, so this needs a heightmap of the same size. Tiles share their edge samples, and their size follows Samples Per Meter (usually 1025 samples, fewer on a terrain whose shorter side is under 1024 / Samples Per Meter meters), so the grid has one sample more than a whole number of tiles: a 4 × 1 km terrain at 4 samples per meter is 16 × 4 tiles of 1025 samples, 16385 × 4097. A heightmap of another size, such as a power-of-two 16384 × 4096, streams while no height modifier reaches it and draws from its height texture once one does; the log names the size to import it at.
  • While a store is cooking, the Scene View shows Preparing terrain pages 42%: terrain name at the top of the view (with "and N more" when several cook at once), and the terrain draws from its height texture as before. When the cook finishes, the terrain switches to its pages within a few frames. A scene that loads while a large store cooks keeps the editor busy, so the banner advances in steps.
  • The game's Player opens the store packed into the exported game and never cooks. A heightmap shipped without a store draws from its height texture, and the Player's log says so.
  • The web build and GPUs without 64-bit shader integers keep drawing from the height texture.

A terrain over one of these limits draws from its height texture, and the log states why, once, with the fix:

  • Too large: "<terrain> (X x Z samples) does not stream its height on this platform: its page table needs ... words, over the platform's cap of ... words. It draws from its height texture. Lower its samples per meter or its size to stream it."
  • Modifiers reach too much of it: "<terrain> does not stream its height on this platform: its height modifiers reach so much of it that their page overlay needs ... bytes, over the platform's cap of ... bytes. It draws from its height texture. Shrink the modifiers' bounds (a terrain-wide modifier reaches every sample) or lower the terrain's samples per meter to stream it." A modifier with no bounds reaches the whole terrain: on an 8 × 2 km terrain at 0.25 m that is 1366 MiB, over the desktop's 512 MiB.
  • Modifiers on a heightmap of another size: "<terrain> does not stream its height while height modifiers reach it: its heightmap's grid (X x Z samples) is not the terrain's tile lattice (X' x Z' samples), on which the modifiers are baked. It draws from its height texture. Import the heightmap at X' x Z' samples to stream it with its modifiers."

An orthophoto as the terrain's albedo

A terrain material normally lays its textures on from three sides and blends them by slope (Projection: Triplanar). That is right for a texture that tiles, such as rock, grass or sand. It is wrong for an image of this particular terrain, such as an orthophoto or a painted basemap: on a cliff the side projections pick the image row by height, so the cliff shows an unrelated part of the photo.

Set the material's Projection to Planar in the terrain material library:

  • Planar lays the image straight down at the terrain's own coordinates, north up: the world's +Z is north, image column 0 is the terrain's edge at the smallest X (west) and image row 0 is the edge at the largest Z (north), which is how an image file stores a north-up photo. An orthophoto cut to the same area as the DEM lies on the relief it was captured with, without flipping it. (The .r32 heightmap is the other way round: its first row is the smallest-Z edge, as above.)
  • The image spans the terrain along each axis independently, 0 to 1 along X and 0 to 1 along Z, so a non-square image goes on a non-square terrain as it is: a 4:1 photo of a 60 × 15 km area at Tiling 1 covers that terrain exactly.
  • A cliff shows the photo stretched down its face. That is the photo's own content at that spot, not another part of the image.
  • Tiling means repeats across the whole terrain for a Planar material: 1 is one image over the whole terrain, and 4 repeats it four times along each side, which turns Planar into a top-down tiled texture. The terrain's Material Tiling (meters per repeat) does not apply. Below 1 the terrain shows only part of the image, enlarged (0.5 shows its north-west quarter); 0 reads as 1.
  • The material's normal and ORM maps use the same projection as its albedo, so they stay registered with it. The terrain's own normal map and splat are read at the terrain's coordinates as always.
  • Hex Tiling stays as you set it. It shuffles the image, which is what a tiling texture wants and what a photo must not have: leave it off for an orthophoto.
  • On a streamed terrain the image covers exactly Size X × Size Z. At Tiling 1 (or less) it is sampled clamped to its edges, so the terrain's borders and the strip where the tile grid runs past the terrain's edge show the image's own edge pixels, not the opposite edge. Above 1 it repeats.
  • Planar is for heightfield terrains. On a planet the terrain's coordinates are per cube face, so a Planar material shades as Triplanar there.
  • A material without an albedo texture is unaffected by its projection; it still shades from its tint.
  • The photo shows only where its material is painted. Ground whose channel is painted with another material (cliffs painted Rock by a surface rule, say) shows that material, not the photo.

From an exported orthophoto band to the terrain

  1. Export the DEM as .r32 with its first row on the south edge (the smallest Z) and import it as above; that is the order a heightmap is read in, and it is the one the orthophoto below is matched to.
  2. Export the orthophoto in the same projection as the DEM, cropped to exactly the DEM's extent (the same west, east, south and north bounds), north up. Image services and GIS exports write north-up by default; do not flip it.
  3. Keep the image's aspect the same as the terrain's: a 60 × 15 km terrain takes a 4:1 image, such as 8192 × 2048.
  4. Drop the image into the project. In its import settings keep Color Space on Auto or sRGB (it is a color map) and Generate Mips on. A terrain material's texture is uploaded uncompressed today, whatever its Compression setting (#3014): an 8192 × 2048 image takes about 85 MiB of GPU memory with its mips.
  5. In the terrain's material library, set the image as a material's Albedo, Projection to Planar, Tiling to 1 and Hex Tiling off, and bind that material to the channel the terrain paints (Grass, by default, on an unpainted terrain). The terrain shows the change at once.

The largest image the GPU can hold is its maximum 2D texture size (Vulkan's maxImageDimension2D): 32768 pixels on current NVIDIA desktop GPUs, 16384 on many others. A 16384-pixel image over 60 km is about 3.7 m per pixel; for finer coverage of part of the area, use a second, smaller terrain with its own image over that part.

Limits today

  • The whole DEM is decoded into memory when the terrain first needs it and stays decoded while used: a 16384 × 4096 .r32 is 256 MiB of CPU memory, decoded on the main thread.
  • A 16-bit PNG is decoded whole, so it holds at most about 1.07 billion grayscale samples (32768 × 32767; fewer with color channels). A larger PNG does not decode, and the Terrain inspector’s Base section says so and gives the fix: export the heightmap as .r32, which has no size limit.
  • Outside the resident window the terrain is drawn from one coarse field over the longer side, so a long, narrow terrain spends most of that field's rows outside itself.
  • The Scene View's Far Clip (camera settings, default 3000 m) is not widened for a large planar terrain: raise it to see one whole.
  • The normal and splat maps are read from above, one texel per terrain sample, so on a near-vertical wall their texels stretch down the slope; a higher Samples Per Meter shortens the stretch. Triplanar material textures are projected from three sides on slopes steeper than about 31° and from above on gentler ground; a Planar material is always projected from above.
  • In Play mode a streamed terrain's colliders are currently built at the world origin.
