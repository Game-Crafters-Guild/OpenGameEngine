Project material shader warm-up

Concept guide · material shaders / editor

A material's shaders compile the first time something draws with them, and that compile is a visible hitch. After a project opens, the editor compiles the shaders of the project's materials in the background, a little at a time, so that opening a scene or dropping a model into it finds them ready. It is always on; there is nothing to configure.

When it runs

A couple of seconds after a project opens, the editor lists the project's materials and then compiles them one material at a time on the background worker lane. It yields to everything else: it waits while shaders a scene actually needs are compiling or other work is queued, and after each material it pauses for nineteen times as long as that material took (at least 100 ms), so it uses about a twentieth of one worker. It is background work and never shows the scene view's compiling-shaders indicator, which counts only compiles something on screen is waiting for. The project is listed once, after it has finished scanning its folder; a material created or edited while the editor is open is warmed when the change arrives. An editor sitting idle does no listing at all.

Opening a different project stops the warm-up of the previous one and starts over for the new project. Nothing is warmed while the editor sits on its startup workspace before a project is chosen.

What is warmed

  • Every .material in the project.
  • The materials embedded in models the project has loaded before on this machine (see below).

For each material the editor compiles the variants a draw asks for: the material's own keywords and lighting model on static, normal-mapped and skinned meshes in the color pass, the glass (transmission) pass for transmissive materials, the editor's material and model previews, and the depth and shadow variants the material draws with. Opaque materials without a vertex modifier draw depth and shadows with one shared pipeline, so they need none of their own; alpha-tested (Mask) materials, materials with a vertex modifier and glass do. The dithered variants a mesh draws while it crossfades between levels of detail are warmed in both. Warm-up only compiles shaders; it does not create runtime materials or load textures.

What can still compile on first use

  • Materials in models that have never been loaded on this machine.
  • Variants for meshes with extra vertex streams (vertex colors, a second UV set, eight bone influences), asset previews with the preview's environment lighting turned on, and materials created at runtime.
  • Variants a view adds for itself: ambient occlusion, screen-space reflections, global illumination probes, screen-space shadows and ray-traced shadows from a volume or view setting, and the motion-vector variants of materials with a vertex modifier.
  • Any variant after the active render pipeline changes its world-pass keywords.

Models

The editor never imports a model just to find its materials. Each time a model loads, it records its imported materials in the project's derived cache, .Cache/ModelMaterials/, and rewrites that record only when the materials changed. The warm-up reads those records. Like the rest of .Cache the folder is safe to delete; the records come back as models load. Nothing is written to the project's AssetDatabase.assetdb.

Players

A packaged game's content is read-only. Loading one of its models records nothing, so its install folder keeps exactly what was shipped, and the warm-up skips its materials. A development Player running from a project folder warms that project the same way the editor does.

Compiled shaders on disk

Compiled shaders are kept as shader packages (.shaderpkg): the compiled stages plus the reflection data that describes their bindings. The editor's compile cache holds one package per compiled variant, and the built-in passes ship as packages next to the executable. Packages are format version 2, which stores the reflection data in binary form.

After upgrading from a build that wrote version 1 packages

  • The first run recompiles each cached shader once, as it is first needed, and writes it back in the new format. Later runs load the cache without compiling.
  • Compile caches you cooked and shipped with a game (material variant cooks, the web editor's material cache) must be cooked again. A runtime without a shader compiler cannot rebuild a version 1 entry and treats it as missing.
  • The built-in packages are rebuilt by the build (target CompileShaderPkgs). For a project or source-package shader, rerun its authoring script with this SDK's ShaderReflect, found in the Tools folder next to the Apps folder that holds the editor and player executables, supplying the compiled shader stages through --vs, --fs or --cs and the package's resolved path through --out. Where the failed load is reported, in a rejected render graph or in a built-in pass's load warning, the error names that path and the relevant action. Loading refuses the stale package; it does not rebuild or overwrite it. A graph rejected when it is selected, or at startup, is replaced by the ForwardPlus graph, or by the built-in default when ForwardPlus is rejected as well; a graph rejected after an edit leaves the pipeline that was running in place. The log names each rejected graph and its failed package.
