Desktop Player source ownership

CONCEPT · build & export / Player · which sources in your project a desktop export owns

One rule for the sources a desktop export compiles: the engine owns the default application and keeps it out of the project, and the project owns everything it wrote itself. Windows and macOS exports prepare the default application in <project>/.Build/Player/Source; nothing is created, refreshed or deleted inside project Assets.

The problem, as the user meets it. An export used to copy the whole Player template directory into Assets/Source — including the browser entry points, which do not compile for a desktop target. The copies then sat in the tree the native gameplay module watches and compiles, so the same translation units were built twice and every later export rewrote files the project now appeared to own. Nothing in the tree said which files were the engine’s and which were the user’s.

Who owns which sources

TreeOwnerWhat export does with it
<project>/.Build/Player/Sourceengine Written and refreshed on every export from the SDK template set. Changed files are rewritten, newly listed companions are added, unchanged files are left alone.
<project>/Assets/Sourceproject Read only. A main.cpp or PlayerApplication.cpp here selects the application and suppresses the generated default entirely; other files there join the source list as helpers.
<project>/Assets (everything else)project Compiled into the native user module and shipped through native module staging. Never linked into the Player a second time.

One manifest, two consumers

Apps/Player/DesktopSources.txt lists the desktop application’s translation units. The repository’s own Player target reads it through ge_read_desktop_player_sources() (cmake/DesktopPlayerSources.cmake), and SDK staging copies exactly those files plus the manifest into SDK/templates/Player. Export reads the staged manifest again in PreparePlayerSources(). Adding a companion file is therefore one edit, and the browser entry points — which belong to the Web Player target — can never reach a desktop export.

A manifest entry is a relative path under the template root with a .cpp or .h extension. Absolute paths, drive letters, backslashes, semicolons and ./.. components are refused, as is an entry naming a file that does not exist. The whole list is validated before anything is written, so a bad manifest fails the export with the offending path instead of leaving a half-written source project behind.

Projects exported by older editors

Older exports copied SDK sources into Assets/Source without an ownership marker. Those files are now treated as project-owned, including modified copies: their filenames cannot establish permission to overwrite or delete them. Export neither migrates nor discards them.

To return to the generated default: compare the old Assets/Source files against the SDK version that produced them, keep any deliberate change, and delete the rest from the project. To keep a custom Player, maintain its companion files as application code — and remove the Web-only translation units an older export left there, because they are now compiled as part of the desktop application.

Use a matching Editor and SDK. A missing manifest, or a companion the manifest names but the SDK does not carry, fails source preparation with the failing path rather than producing a partial source project.
